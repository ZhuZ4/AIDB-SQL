# data-link

将用户问题转换为可用于 SQL 生成的 M-Schema。

## 工作目标

输出一个经过筛选的 M-Schema，而不是一份无差别的 schema 转储。

## 关键词提取

在调用任何召回工具之前，先把用户问题（与 Evidence）拆成结构化的"五维"关键词 JSON。
这套提取既驱动后续 `sql_db_value_lookup` 的短语，也作为下游 `database-query-helper`
写 SELECT 时的**投影白名单**——所以必须在召回开始之前完成，并以 fenced ``json`` 块
原文呈现在你的回复里。

### 五维定义

- **查询目标**：本题要"看到"的字段，包含指标（可统计的数值型术语）和维度名称
  （分类属性）。不包含统计相关的动词（"统计""平均""最大"等）。Evidence 公式整体
  视为**一个**查询目标字段（即使分子分母涉及多列）。
- **分组条件**：主要是离散型维度名称——题目要求按某维度展示时才填。
- **过滤条件**：维度名称对应的具体维度取值，或指标的数值条件限定；
  形如 `{"维度": ["取值"]}`。
- **排序目标**：可排序的指标或维度字段；只填需要 `ORDER BY` 的字段。
- **统计函数**：聚合相关动词（最大/最小/前 N/总数/平均等）。

### 关键词的判定规则

- 关键词只能是**名词或名词短语**。
- **不能**作为关键词：常见停用词、副词、表示数值的数量词、统计相关的动词。
- 如果用户提问较口语化，请用更专业的术语来表示（可借助"当前知识库相关术语"
  里的措辞）。
- 用户的问题与已知术语不一定一一对应，但已知术语提供了标准表达方式参考。
- 提取顺序与现有"召回原则"的关键词优先级一致：Evidence 反引号列名 > Evidence
  公式列短语 > 用户问题中的多词业务短语 > schema-exploration 已确认的短语；
  每一级的产物都回填到上述五维 JSON 的对应字段。

### 输出格式（硬约束）

```json
{
  "查询目标": ["..."],
  "分组条件": ["..."],
  "过滤条件": {"维度名": ["取值"]},
  "排序目标": ["..."],
  "统计函数": ["..."]
}
```

字段必须齐全——没有就给空数组 `[]` 或空对象 `{}`，不要省略键。

## 默认流程

1. **结构化关键词提取**：按上一节规则输出五维 JSON（fenced ``json`` 块），不要省略字段
2. 用 JSON 中"查询目标 + 分组条件 + 过滤条件的 key 与 value + 排序目标"里的**每个短语**
   单独调用一次 `sql_db_value_lookup(phrase=...)`；严禁把多个短语拼成字符串或列表一次性传入
3. 从召回结果中挑选真正相关的业务列和必要 join key
4. 使用 `add_schema` 累积这些列
5. 调用 `build_linked_mschema` 输出 M-Schema
6. 在交接给下游之前，把 Step 1 的五维 JSON **原文**再复述一次到回复末尾，便于
   `database-query-helper` 直接按"查询目标"决定 SELECT 投影

## 召回原则

- 每次 `sql_db_value_lookup` 只传一个短语，保持原始语言（严禁翻译）
- 若一个短语召回噪声大，先改写短语本身（同义词、缩写展开、单复数），再考虑借助 `schema-exploration`
- 关键词提取优先级：
  - Evidence 中反引号括起的完整列名（逐个作为 phrase 调用）
  - Evidence 公式里出现的业务列短语
  - 用户问题中的多词业务短语
  - 已经由 `schema-exploration` 确认过的完整列短语
- 只把当前问题真正需要的列加入链接架构
- 必要时补入 join key，但不要把候选表的全部列都加入
- 上述四级关键词每提取出一项，都要回填到 Step 1 五维 JSON 的对应字段；Evidence 公式整体作为**一个**查询目标条目，不要拆成分子分母两条进过滤条件

## 何时借助 schema-exploration

仅当以下情况出现时，才加载 `schema-exploration`：

- `sql_db_value_lookup` 召回结果过噪
- 列名是 3 到 4 个单词组成的完整短语，当前召回无法确认
- 需要确认候选表之间的关系或 join 路径
- 需要区分相似列（例如 mailing / physical / home）

借助 `schema-exploration` 时，只检查：

- 候选表
- 完整列名和列注释
- 必要关系

不要把 `sql_db_schema` 返回的所有字段都加入 `add_schema`。

## 输出要求

- 结束时必须调用 `build_linked_mschema`
- M-Schema 应只包含当前问题需要的列
- M-Schema 中允许保留必要的 join key 和公式列

## 禁止事项

- 不要执行 `sql_db_query`
- 不要使用旧的召回验证或裁剪路径
- 不要把 schema-exploration 结果整批导入链接架构

## 交接给下游

完成后，把问题和 M-Schema 交给 `database-query-helper`，由它生成单条初始 SQL。
